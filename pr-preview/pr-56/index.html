Write the rules once.

x.uma is a matcher engine implementing the xDS Unified Matcher API. One config, one Rust engine, three languages, one conformance suite proving they agree.

It runs here

This is the real engine: rumi, compiled to WebAssembly and running in your browser, loading the config beside it. Change the method to POST, or to something else entirely, and watch the decision change.

loadinginstantiating the engine

Editable. Change either side and the result updates as you type.

Rules are tried in order and the first match wins. When nothing matches, on_no_match decides. That is the whole evaluation model.

The same config, three runtimes

The config above is data, not code. Every runtime hands it to the same engine and gets the same answer.

Rust

let matcher = registry.load_typed_matcher(config, &actions)?;
matcher.evaluate(&ctx)   // Some("read-handler")

Python

matcher = KvMatcher.from_config(config)
matcher.evaluate(ctx)    # "read-handler"

TypeScript

const matcher = KvMatcher.fromConfig(config);
matcher.evaluate(ctx);   // "read-handler"

One engine, three runtimes

Pick by runtime. Every package is the same Rust engine; the bindings add a host-language surface, not a second implementation.

PackageLanguageWhat it is
rumi-coreRustThe engine. Reference implementation.
xuma-crustPython 3.12+The engine, bound through PyO3.
xuma-crustTypeScriptThe engine, compiled to WebAssembly.

All three run the same conformance fixtures from spec/tests/. A binding that disagrees with the engine fails its own build.

How a decision is made

Context  →  DataInput  →  MatchingData  →  InputMatcher  →  bool
            domain-        erased           domain-
            specific                        agnostic

An ExactMatcher does not know whether it is matching an HTTP path, a Claude Code hook event, or your own domain. It matches data. Extracting that data from a context is a separate port, which is why one matcher works everywhere.
